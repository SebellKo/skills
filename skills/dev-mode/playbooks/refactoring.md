# 리팩터링

[dev-mode의 공통 절차](../SKILL.md)에 따라 시작 전 Issue·화면 근거를 준비하고, 아래 작업 후 결과 PR을 게시한다.

외부에서 관찰되는 동작과 계약을 유지하면서 내부 구조를 개선한다.

1. 유지할 동작·인터페이스·오류·데이터 형식과 개선할 구조를 정한다. `qa-feature`의 변경 전 관찰과 기존 테스트에서 기준을 확보한다. 기존 문제를 이번에 고칠 동작으로 자동 편입하지 않는다.
2. 구조를 바꾸기 전에 관련 동작을 고정하는 검사가 충분한지 확인한다. 부족하면 `implement-code`의 담당자에게 먼저 현재 동작을 확인하는 작은 테스트·입출력 비교 등을 준비하게 한다. 타입 검사나 린트만으로 동작 보존 기준을 대신하지 않는다.
3. `design-code`로 책임·인터페이스·상태 배치와 변경 경로를 정한다. 이미 합의된 유효한 설계는 이어받는다. 단순 이름 변경·기계적 이동처럼 구조 선택이 없는 작업은 설계 비교를 생략할 수 있다.
4. `implement-code`로 구현한다. 순서와 검증 지점은 메인과 구현 담당자가 선택한 원칙에 따른다. 계획된 이전에서 일시적 불완전 상태가 필요하면 작업 공간을 격리하고 공유 환경이나 범위 밖의 소비자를 깨뜨리지 않는다.
5. `review-code`로 동작 보존과 구조의 실제 개선을 확인한다. 호출자가 알아야 할 복잡성, 중복 정책, 분산된 변경 지점 중 무엇이 줄었는지 근거를 확인한다.
6. `qa-feature`와 필요한 이전·이후 비교 검사로 관련 동작이 동일한지 확인한다. 입력·조건이 다른 결과를 동등성 근거로 사용하지 않는다.

현재 요청에 포함되지 않은 기능이나 버그는 발견 사실과 영향을 보고한다. 사용자가 수정 범위에 포함하면 별도 의도로 구분해 해당 플레이북으로 연결한다. 구조 개선의 이점이 확인되지 않으면 변경안을 다시 검토한다. 되돌리기가 필요해도 사용자나 다른 작업자의 변경을 함께 되돌리지 않는다.

**완료:** 유지할 계약과 동작을 검증했고 현재 코드의 구체적인 구조적 비용을 줄였다. 컴파일 성공이나 파일 수 감소만으로 완료를 판단하지 않는다.
