# Dev Mode

`$dev-mode` 또는 이 스킬을 사용하라는 명시적 요청을 진입점으로 삼는다. 적용 범위는 그 작업과 이어지는 수정·검증이다. 별개의 새 요청에 자동으로 적용하지 않는다. 같은 메인이 전체 진행과 완료 판단을 맡는다.

## 1. 플레이북을 선택한다

요청과 관련 코드를 확인하고, 선택한 흐름과 이유를 짧게 알린 뒤 해당 플레이북을 읽어 진행한다. 사용자가 플레이북을 지정하면 그 선택에서 시작하되, 조사 결과 성격이 다르면 이유와 전환할 흐름을 설명한다.

| 플레이북 | 선택 기준 |
| --- | --- |
| [기능 구현](playbooks/feature.md) | 새로운 사용자 동작이나 기존 동작의 의도적인 변경 |
| [버그 수정](playbooks/bug-fix.md) | 기대한 동작과 실제 동작의 불일치 |
| [단순 수정](playbooks/small-change.md) | 목표가 명확하고 영향이 국소적인 문구·스타일·설정 등의 수정 |
| [리팩터링](playbooks/refactoring.md) | 외부에서 관찰되는 동작을 유지하는 내부 구조 개선 |

변경 줄 수만으로 단순 수정을 고르지 않는다. 권한·저장 데이터·공유 상태·API 계약에 영향을 주면 의도에 맞춰 기능 구현이나 버그 수정으로 분류한다. 복합 요청은 서로 다른 의도를 구분해 순서를 정한다. 버그 수정을 리팩터링에 섞거나 작은 UI 변경을 이유로 새 기능을 단순 수정으로 축소하지 않는다.

## 2. 필요한 스킬을 연결한다

현재 단계에서 사용할 스킬을 읽고 적용한다. 아래 스킬은 별도로 설치되어 있어야 한다. 상대 링크에서 찾지 못하면 설치된 스킬 목록에서 같은 이름을 찾고, 필요한 스킬이 없으면 누락을 알린다. 세부 지침을 추측해서 대체하지 않는다.

| 스킬 | 이어받을 결과 |
| --- | --- |
| [clarify-requirements](../clarify-requirements/SKILL.md) | 목표·범위·요구사항·완료 조건·미결정 |
| [design-code](../design-code/SKILL.md) | 선택한 구조·인터페이스·상태 소유권·변경 영향 |
| [implement-code](../implement-code/SKILL.md) | 실제 변경·구현 검증·남은 문제 |
| [review-code](../review-code/SKILL.md) | 검증된 결함·구조와 전제 문제·확인 필요 항목 |
| [qa-feature](../qa-feature/SKILL.md) | 변경 전 관찰 또는 변경 후 기능·회귀 검증 |

별도의 단계 관리자 에이전트를 만들지 않는다. 메인이 각 스킬의 조정자 역할을 수행하고, 그 스킬이 정한 작업자를 직접 스폰한다. 모델·추론 수준·역할 수·독립성은 각 스킬의 설정을 따른다. 현재 스폰 도구가 `agent_type`을 지원하지 않으면 역할과 책임을 작업 설명에 넣고 지원하는 인자만 사용한다.

필요한 사용자 결정과 자료, 코드 상태, 기준 동작, 담당 범위와 기대 결과를 작업자에게 전달한다. 슬롯이 부족하면 대기 중인 역할을 순차 실행하며, 역할을 생략해 통과로 처리하지 않는다. 공유 작업 트리·앱·브라우저 세션을 수정 작업과 검증 작업이 동시에 바꾸지 않게 한다.

웹 직접 확인은 해당 스킬의 ego lite 지침을 따른다. 인증이 필요하면 QA의 로컬 계정 참조 지침을 적용하고 계정값을 공유 맥락·산출물·GitHub에 복사하지 않는다.

## 3. 결과를 이어받고 문제에 맞춰 돌아간다

기존 요구사항·설계·구현·검증 결과가 있으면 현재 요청과 코드에도 유효한지 확인하고 남은 단계부터 이어간다. 이미 합의한 결정을 다시 묻거나 완료된 단계를 형식적으로 반복하지 않는다. 변경 전 실행 관찰이 없으면 과거 기준을 만들어내지 않는다.

메인은 선택한 플레이북, 완료 조건, 주요 결정, 현재 코드 상태와 검증 근거, 남은 문제를 대화 맥락에 간결하게 유지한다. 별도 진행·QA 문서를 기본으로 만들지 않는다. 단계마다 승인을 묻지 않으며, 사용자만 정할 수 있는 제품 동작·범위 결정은 확인하고 그 결정에 의존하지 않는 작업은 계속한다.

리뷰 지적은 근거를 확인해 수정 필요·제안·확인 필요·기각으로 판단한다. 제안을 전부 구현하거나 기대 조건을 낮춰 검증을 통과시키지 않는다. 실패 원인에 맞는 단계만 다시 진행한다.

- 기대 동작이나 자료가 충돌하면 `clarify-requirements`로 해당 결정을 정리한다.
- 인터페이스·책임·상태 배치가 원인이면 `design-code`로 관련 설계를 재검토한다.
- 합의한 동작을 코드가 어기면 `implement-code`로 수정하고 관련 검사·리뷰·QA를 다시 수행한다.
- 실행 환경이나 관찰 도구가 원인이면 해당 조건부터 바로잡고 재검증한다.

검증 결과는 실행한 코드와 환경에 연결한다. 수정 후 영향받는 결과를 재검증하고, 영향을 받지 않은 결과는 근거와 함께 재사용한다. 같은 실패가 반복되면 가정과 원인을 다시 조사한다. 필요한 결정·접근·환경을 확보하지 못하면 막힌 범위와 다음 조건을 보고하며 근거 없는 재시도를 반복하지 않는다.

## 4. 완료를 판단한다

선택한 플레이북의 완료 조건, 필요한 구현 검사, 채택한 리뷰 수정 사항, 필요한 QA가 최종 코드에서 충족됐는지 확인한다. 생략 가능한 단계는 생략 이유를 남기며, 실행하지 못한 필수 검증을 생략 가능으로 바꾸지 않는다.

결과에는 바뀐 동작 또는 구조, 실제 검증과 근거, 남은 문제를 담는다. 필수 검증이 남으면 “구현 완료, 검증 미완료”처럼 상태를 구분한다. PR 생성·병합·배포는 요청된 범위에 포함될 때만 연결한다.
