# Dev Mode

`$dev-mode` 또는 이 스킬을 사용하라는 명시적 요청을 진입점으로 삼는다. 적용 범위는 그 작업과 이어지는 수정·검증이다. 별개의 새 요청에 자동으로 적용하지 않는다. 같은 메인이 전체 진행과 완료 판단을 맡는다.

기본 완료 범위에는 작업 Issue 등록·갱신과 결과 PR 생성·갱신이 포함된다. 이 스킬을 명시적으로 호출하면 해당 작업의 게시를 진행하고 단계마다 재승인을 묻지 않는다. 사용자가 로컬 작업만 요청하거나 게시를 제외하면 그 범위를 따른다. 병합·배포는 별도 요청 범위다. 개별 작업 스킬을 단독 호출한 경우에는 이 게시 흐름을 자동 적용하지 않는다.

## 1. 플레이북을 선택한다

요청과 관련 코드를 확인하고, 선택한 흐름과 이유를 짧게 알린 뒤 해당 플레이북을 읽어 진행한다. 사용자가 플레이북을 지정하면 그 선택에서 시작하되, 조사 결과 성격이 다르면 이유와 전환할 흐름을 설명한다.

| 플레이북 | 선택 기준 |
| --- | --- |
| [기능 구현](playbooks/feature.md) | 새로운 사용자 동작이나 기존 동작의 의도적인 변경 |
| [버그 수정](playbooks/bug-fix.md) | 기대한 동작과 실제 동작의 불일치 |
| [단순 수정](playbooks/small-change.md) | 목표가 명확하고 영향이 국소적인 문구·스타일·설정 등의 수정 |
| [리팩터링](playbooks/refactoring.md) | 외부에서 관찰되는 동작을 유지하는 내부 구조 개선 |

변경 줄 수만으로 단순 수정을 고르지 않는다. 권한·저장 데이터·공유 상태·API 계약에 영향을 주면 의도에 맞춰 기능 구현이나 버그 수정으로 분류한다. 복합 요청은 서로 다른 의도를 구분해 순서를 정한다. 버그 수정을 리팩터링에 섞거나 작은 UI 변경을 이유로 새 기능을 단순 수정으로 축소하지 않는다.

## 2. Issue와 변경 전 근거를 준비한다

네 플레이북 모두 다음 공통 절차를 적용한다.

1. 목표와 대략적인 범위, 대상 저장소를 확인하고 [create-issue](../create-issue/SKILL.md)를 읽어 Issue를 등록하거나 기존 작업 Issue를 이어받는다. 먼저 풀어야 할 제품 결정만 `clarify-requirements`로 확인하고, 요구사항이 구체화되거나 바뀌면 같은 Issue를 갱신한다. 상세 구현 계획은 Issue에 넣지 않는다.
2. 기준·작업 브랜치와 기존 변경을 확인한다. 관련 작업 브랜치를 재사용하거나 저장소 관례에 맞게 준비한다. 기존 작업을 덮어쓰거나 공유 기준 브랜치에 직접 결과를 쌓지 않는다. Issue와 작업 브랜치를 이후 담당자에게 전달한다.
3. 시각적 비교와 실제 사용자 흐름 확인이 필요한지 정한다. 시각적 비교가 필요하면 코드 수정 전에 `qa-feature`에 [PR 증거 수집](../qa-feature/references/pr-evidence.md)을 요청해 변경 전 화면을 확보한다. 플레이북의 기존 기준 확인과 합쳐 수행하고, 단순 수정은 필요한 화면만 캡처한다. 이전 화면을 얻을 수 없으면 이유와 비교 한계를 남기고 확인 가능한 작업은 계속한다.

Issue 게시가 권한·인증 등으로 막히면 작성한 내용과 원인을 보존하고 독립적으로 가능한 작업은 계속한다. 게시가 해결되지 않은 상태를 전체 완료로 보고하지 않는다.

## 3. 필요한 스킬을 연결한다

메인은 흐름을 조정하면서 아래 조건에 맞는 원칙 파일을 직접 읽는다. 이미 현재 맥락에서 읽은 파일은 다시 읽지 않는다. 원칙의 적용은 합의한 작업 범위 안으로 한정한다.

| 적용 상황 | 읽을 원칙 |
| --- | --- |
| 여러 단계와 의존 작업을 진행할 때 | [sequence-verifiable-units](../principles/principle-sequence-verifiable-units/SKILL.md) |
| 작업자를 나누거나 긴 자료·로그를 이어받을 때 | [guard-the-context-window](../principles/principle-guard-the-context-window/SKILL.md) |
| 단계 경계를 정한 재작성·이전을 진행할 때 | [outcome-oriented-execution](../principles/principle-outcome-oriented-execution/SKILL.md) |
| 같은 전제의 수정이 같은 검사에서 두 번 이상 실패할 때 | [attack-the-premise](../principles/principle-attack-the-premise/SKILL.md) |
| 최종 결과를 완료로 판단할 때 | [prove-it-works](../principles/principle-prove-it-works/SKILL.md) |

현재 단계에서 사용할 스킬을 읽고 적용한다. 아래 스킬은 별도로 설치되어 있어야 한다. 상대 링크에서 찾지 못하면 설치된 스킬 목록에서 같은 이름을 찾고, 필요한 스킬이 없으면 누락을 알린다. 세부 지침을 추측해서 대체하지 않는다.

| 스킬 | 이어받을 결과 |
| --- | --- |
| [create-issue](../create-issue/SKILL.md) | 작업 Issue URL·요구사항·제약·완료 조건 |
| [clarify-requirements](../clarify-requirements/SKILL.md) | 목표·범위·요구사항·완료 조건·미결정 |
| [design-code](../design-code/SKILL.md) | 선택한 구조·인터페이스·상태 소유권·변경 영향 |
| [implement-code](../implement-code/SKILL.md) | 실제 변경·구현 검증·남은 문제 |
| [review-code](../review-code/SKILL.md) | 검증된 결함·구조와 전제 문제·확인 필요 항목 |
| [qa-feature](../qa-feature/SKILL.md) | 변경 전 관찰 또는 변경 후 기능·회귀 검증 |
| [create-pr](../create-pr/SKILL.md) | Issue와 검증 근거를 포함한 결과 PR URL·게시 상태 |

별도의 단계 관리자 에이전트를 만들지 않는다. 메인이 각 스킬의 조정자 역할을 수행하고, 그 스킬이 정한 작업자를 직접 스폰한다. 모델·추론 수준·역할 수·독립성은 각 스킬의 설정을 따르고 역할과 책임은 작업 설명에 넣는다.

각 단계 스킬은 자체 선택표로 필요한 원칙을 읽는다. 메인은 작업자에게 역할 지침과 선택한 원칙의 실제 파일 경로를 전달하고 직접 읽도록 한다. `dev-mode`에서 읽은 내용이 작업자에게 자동 상속된다고 가정하지 않는다.

필요한 사용자 결정과 자료, 코드 상태, 기준 동작, 담당 범위와 기대 결과를 작업자에게 전달한다. 슬롯이 부족하면 대기 중인 역할을 순차 실행하며, 역할을 생략해 통과로 처리하지 않는다. 공유 작업 트리·앱·브라우저 세션을 수정 작업과 검증 작업이 동시에 바꾸지 않게 한다.

웹 직접 확인은 해당 스킬의 ego lite 지침을 따른다. 인증이 필요하면 QA의 로컬 계정 참조 지침을 적용하고 계정값을 공유 맥락·산출물·GitHub에 복사하지 않는다.

## 4. 결과를 이어받고 문제에 맞춰 돌아간다

기존 요구사항·설계·구현·검증 결과가 있으면 현재 요청과 코드에도 유효한지 확인하고 남은 단계부터 이어간다. 이미 합의한 결정을 다시 묻거나 완료된 단계를 형식적으로 반복하지 않는다. 변경 전 실행 관찰이 없으면 과거 기준을 만들어내지 않는다.

메인은 선택한 플레이북, 완료 조건, 주요 결정, 현재 코드 상태와 검증 근거, 남은 문제를 간결하게 유지한다. 별도 진행·QA 문서를 기본으로 만들지 않는다. 단계마다 승인을 묻지 않으며, 사용자만 정할 수 있는 제품 동작·범위 결정은 확인하고 독립적으로 할 수 있는 작업은 계속한다.

변경 전 캡처와 비교 조건을 보존해 최종 QA에 전달한다. QA에는 변경 후 화면, 필요한 사용자 확인 순서와 진입 표시를 함께 요청한다. 요구사항·범위가 바뀌면 Issue도 갱신하고, 이미 수행한 QA나 게시된 이미지가 최종 코드를 설명하는지 다시 확인한다.

리뷰 지적은 근거를 확인해 수정 필요·제안·확인 필요·기각으로 판단한다. 제안을 전부 구현하거나 기대 조건을 낮춰 검증을 통과시키지 않는다. 실패 원인에 맞는 단계만 다시 진행한다.

- 기대 동작이나 자료가 충돌하면 `clarify-requirements`로 해당 결정을 정리한다.
- 인터페이스·책임·상태 배치가 원인이면 `design-code`로 관련 설계를 재검토한다.
- 합의한 동작을 코드가 어기면 `implement-code`로 수정하고 관련 검사·리뷰·QA를 다시 수행한다.
- 실행 환경이나 관찰 도구가 원인이면 해당 조건부터 바로잡고 재검증한다.

검증 결과는 실행한 코드와 환경에 연결한다. 수정 후 영향받는 결과를 재검증하고, 영향을 받지 않은 결과는 근거와 함께 재사용한다. 반복 실패에서는 선택표의 전제 검증 원칙을 담당자도 읽고 적용하게 한다. 필요한 결정·접근·환경을 확보하지 못하면 막힌 범위와 다음 조건을 보고한다.

## 5. 결과 PR을 게시하고 완료를 판단한다

선택한 플레이북의 완료 조건, 필요한 구현 검사, 채택한 리뷰 수정 사항, 필요한 QA가 최종 코드에서 충족됐는지 확인한다. 계획된 이전은 `outcome-oriented-execution`의 목표 상태와 대조한다. 의도적으로 남길 호환성은 계약과 이유를 확인한다. 생략 가능한 단계는 이유를 남기며, 실행하지 못한 필수 검증을 생략 가능으로 바꾸지 않는다.

게시를 제외하지 않았다면 [create-pr](../create-pr/SKILL.md)를 읽고 관련 Issue, 최종 변경, 검증 결과, 캡처 파일과 사용자 확인 절차를 전달해 PR을 생성·갱신한다. 같은 작업의 PR을 중복 생성하지 않는다. 필수 검증·근거가 남았으면 Draft와 미완료 이유를 명시하며, 게시 실패를 로컬 구현 완료로 덮지 않는다. 변경이 불필요하다고 확인됐다면 빈 PR을 만들지 않고 그 근거와 Issue의 후속 처리 사항을 보고한다.

최종 결과에는 Issue·PR 링크, 바뀐 동작 또는 구조, 실제 검증과 근거, 남은 문제를 담는다. 필수 검증이 남으면 “구현 완료, 검증 미완료”처럼 상태를 구분한다. 실제 PR의 본문·이미지·Assignee·게시 상태까지 확인해야 게시 단계가 완료된다. Issue는 PR 생성만으로 종료하지 않으며 병합·배포를 자동 수행하지 않는다.
