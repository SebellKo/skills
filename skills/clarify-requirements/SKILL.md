# 요구사항 정리

사용자가 아는 내용과 제공한 자료에서 시작한다. 기존 요구사항과 결정이 있으면 이어받아 필요한 부분을 보완한다.

ISO 24495-1:2023의 쉬운 언어 원칙에 따라 사용자 용어와 중요한 결론을 앞에 두고, 한 항목에는 하나의 동작을 담는다.

## 1. 자료에서 사실을 찾는다

- 대화에서 목표, 대상 사용자, 현재 문제, 원하는 결과, 제약과 이미 결정한 사항을 추린다.
- 디자인과 백엔드 자료가 있으면 [자료 조사 기준](references/evidence.md)을 읽는다. 전체 저장소 링크를 받아도 관련 진입점, 계약, 테스트와 호출 경로로 탐색 범위를 좁힌다.
- 코드나 자료에서 알아낼 사실은 직접 조사한다. 접근하지 못한 자료는 미확인으로 기록하고, 결정에 꼭 필요한 부분만 사용자에게 요청한다. 확인 가능한 부분은 계속 정리한다.
- 중요한 근거에는 디자인 노드, PR, 파일·심볼·커밋 등 다시 찾을 수 있는 위치를 붙인다. 코드에서 읽은 동작과 실행해서 확인한 동작을 구별한다.

## 2. 이해한 목표와 차이를 보여 준다

질문 전에 누구의 어떤 문제를 어떤 결과로 해결하려는지 짧게 재진술하고, 핵심 흐름을 사용자 행동 순서로 설명한다.

내용을 **사용자 결정**, **자료에서 확인한 사실**, **제안·추정**, **미결정**으로 구분한다. 사용자 설명, 디자인, 백엔드가 충돌하면 각 근거와 사용자에게 생기는 차이를 보여 준다. 현재 구현을 원하는 요구사항으로 단정하지 않는다.

## 3. 남은 결정을 묻는다

[grill-me 인터뷰 지침](references/grill-me.md)에 따라 동작, 범위 또는 완료 조건이 달라지는 결정을 질문한다.

백엔드가 지원하지 않는 동작은 제품 요구사항과 별도로 의존성에 기록한다. API 변경, 임시 동작, 범위 조정 중 무엇을 택할지는 제품 결정으로 다룬다.

## 4. 요구사항을 정리한다

작업 크기에 맞춰 아래 내용을 하나의 정리본에 담는다. 짧은 작업은 채팅으로 충분하다. 저장 위치가 정해져 있으면 그 위치를 사용하고, 기존 요구사항 문서가 있으면 갱신한다.

- **목표와 범위:** 대상 사용자, 해결할 문제, 포함할 동작, 합의한 제외 항목.
- **요구사항:** `R1`처럼 안정적인 번호, 행동 주체와 조건, 기대 결과, 상태·권한·실패 시 동작 중 관련 항목, 근거와 결정 상태. 삭제한 번호를 다른 요구사항에 재사용하지 않는다.
- **완료 조건:** 각 요구사항 번호에 연결한 구체적 입력·행동·관찰 가능한 결과. 정상 경로와 중요한 실패·경계 상황을 포함한다. “잘 동작한다”, “빠르다” 같은 표현은 검증 가능한 결과로 바꾸고, 근거 없는 성능 수치는 만들지 않는다.
- **의존성과 미결정:** 필요한 API·디자인·정책, 확인할 주체, 영향을 받는 작업. 담당자를 모르면 임의로 지정하지 않는다.
- **주요 결정:** 선택, 이유, 근거. 변경한 결정은 바뀐 이유와 영향을 남긴다.

## 5. 정리본을 확인한다

출처 없는 사실, 숨은 추정, 모순, 관찰할 수 없는 완료 조건을 점검한다. 중요한 제품 결정이 남아 있으면 **초안**으로 표시한다. 확정된 내용과 남은 항목을 구분해 제시하고, 아직 확인받지 않은 결정에 대해 공통 이해를 확인한다.
