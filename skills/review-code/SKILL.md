# 코드 리뷰

메인이 같은 코드와 의도를 세 리뷰어에게 전달하고 각 지적을 검증한다. PR·diff·코드와 사용자 설명으로 시작하며, 기존 요구사항·설계·QA 결과가 있으면 판단 근거로 활용한다.

리뷰는 제품 코드를 수정하지 않는다. 재현용 테스트나 스크립트는 지정한 임시 공간에서 작성할 수 있다. 리뷰 요청만으로 커밋, PR 댓글 게시, 병합을 수행하지 않는다.

## 1. 리뷰 대상과 의도를 맞춘다

사용자가 지정한 범위를 우선한다. PR이면 실제 기준 브랜치와 대상 커밋을 확인한다. 로컬 변경이면 기준 브랜치와의 공통 조상부터 현재 작업 트리까지 살피고, staged·unstaged 변경과 작업에 관련된 추가 파일을 포함한다. 기준을 확인할 수 없으면 임의의 브랜치를 가정하지 않는다. 명시적으로 기존 코드 자체를 검토하는 요청이면 diff 없이 해당 범위를 리뷰한다.

기대 동작, 유지할 계약, 변경 이유를 설명·코드·테스트에서 확인한다. 결함 판정이 달라지는 제품 의도만 사용자에게 묻는다. 연결된 호출부, 공유 상태, 외부 계약과 테스트도 살펴 변경 파일 밖의 영향을 확인한다.

세 리뷰어가 같은 버전을 보도록 대상 커밋과 미커밋 변경을 고정한다. 사용자 작업 트리를 checkout·reset하지 않는다. 재현을 위해 쓰기가 필요하면 동일한 시작 상태를 가진 별도 worktree나 복사본을 제공한다. 커밋만 복제해 미커밋 변경이 빠지지 않게 하고, 비밀 파일이나 무관한 데이터를 함께 복제하지 않는다. 순수 읽기는 같은 대상을 공유해도 된다.

## 2. 세 리뷰어를 독립적으로 실행한다

다음 역할을 각각 한 명씩 스폰한다. 구현을 담당한 에이전트를 리뷰어로 재사용하지 않는다.

| 역할 | 제출할 내용 | 전달할 지침 |
| --- | --- | --- |
| Interrogate | 실행으로 재현한 동작 결함 | [interrogate](references/interrogate.md) |
| 구조·유지보수 리뷰어 | 인터페이스, 책임·상태 소유권, 딥모듈과 유지보수 비용의 문제 | [structure](references/structure.md) |
| Devil’s critic | 변경의 필요성과 전제에 대한 근거 있는 이의 | [critic](references/critic.md) |

모든 호출에 `model: "gpt-6.2-sol"`, `reasoning_effort: "high"`, `fork_turns: "none"`을 명시하고 역할은 작업 설명에 넣는다. 가능한 역할은 병렬로 실행하고, 슬롯이 부족하면 나머지를 순차 실행한다. 모델이나 위임 기능을 사용할 수 없으면 제약을 알리고 대안을 확인한다. 다른 모델이나 메인의 리뷰로 조용히 대체하지 않는다.

각 리뷰어에게 역할 지침과 다음 맥락을 전달한다.

- 사용자 목적, 기대 동작과 계약, 변경 이유, 명시된 범위.
- 동일한 대상 버전·diff·자료 위치, 관련 호출부·테스트, 저장소 지침과 해당 작업에 적용할 스킬·문서. 적용 자료는 변경 내용과 저장소 요구에 따라 고르고, 역할 밖의 전체 원문을 일괄 전달하지 않는다.
- 작업 경로, 실행 방법과 환경, 재현 파일을 작성할 위치.
- 제품 코드와 다른 작업자의 변경을 보존하고, 추가 에이전트를 스폰하지 않을 책임.
- 첫 결과를 제출하기 전에는 다른 리뷰어의 결론을 보지 않을 조건.

역할과 원칙은 살펴볼 질문이며 문제를 찾아낼 의무가 아니다. 담당 관점에서 검토한 뒤 지적이 없으면 확인한 범위와 판단 근거만 짧게 반환한다. 지적이 없다는 이유로 추가 탐색을 시키거나, 원칙별 코멘트와 역할별 개수를 채우지 않는다. 다른 관점의 유효한 문제는 담당 관점의 지적 유무와 관계없이 전달할 수 있으며 근거의 종류를 구분한다.

변경 리뷰에서는 새로 생기거나 악화된 문제를 대상으로 한다. 기존 문제는 이번 변경의 영향과 구분한다. 코드 자체를 검토하는 요청에서는 지정 범위의 현재 문제를 다룬다.

## 3. 메인이 지적을 검증한다

- **동작 결함:** 같은 대상 코드에서 재현 명령을 직접 다시 실행하고, 기대 결과가 요구사항·계약에 근거하는지 확인한다. 변경 전후 차이나 직접 만든 테스트의 실패만으로 결함을 확정하지 않는다. 의도된 변경, 환경·도구 오류, 기존 실패는 제외하고 실행이나 계약 근거가 부족한 후보는 확인 필요로 구분한다.
- **구조·유지보수 문제:** 지적한 인터페이스와 호출부를 읽어 책임 누출, 중복 정책, 추적해야 할 계층·상태 등 현재 비용을 확인한다. 실패 테스트를 억지로 요구하거나 특정 패턴을 쓰지 않았다는 이유로 결함으로 취급하지 않는다.
- **전제에 대한 이의:** 요구사항과 기존 계약, 변경 구문을 대조한다. 제안한 축소·삭제가 필요한 동작을 보존하는지 확인한다. 정보 부족을 불필요한 변경의 증거로 삼지 않는다.

한 명만 발견한 문제도 근거가 유효하면 남긴다. 같은 원인의 지적은 합치고, 서로 충돌하면 코드와 재현 결과로 판단한다. 리뷰어의 숫자, 확신에 찬 표현, 같은 모델의 동의를 근거로 삼지 않는다.

재현은 격리된 데이터와 자원에서 수행한다. 브라우저 재현이 필요하면 설치된 `ego-browser` 지침에 따라 ego lite를 사용한다. 리뷰 범위를 넘어서는 외부 발송·결제·사용자 데이터 변경은 수행하지 않는다. 자신이 만든 실행 자원만 정리하고 검토에 필요한 증거는 보존한다.

리뷰 중 대상 코드가 바뀌면 영향을 받는 지적과 검사를 최신 대상에서 다시 확인한다. 일부 역할이나 실행 경로가 미완료면 그 범위를 남기고 완료한 것처럼 보고하지 않는다.

## 4. 통합 결과를 전달한다

결론과 중요한 지적부터 설명한다. 검증된 동작 결함, 근거가 확인된 구조·전제 문제, 확인이 필요한 항목을 구분하되 빈 항목을 억지로 만들지 않는다.

각 지적에는 파일·줄, 발생 조건 또는 구조적 문제, 기대와 실제의 차이, 영향, 근거와 필요한 수정 방향을 담는다. 동작 결함은 재현 명령·실제 출력·기대 결과도 제공한다. 수정이 필요한 문제에만 P0(즉각 대응할 치명적 문제), P1(높은 영향의 문제), P2(범위가 제한된 실질적 문제)를 붙인다. 간소화 제안과 계약 확인 항목을 확정 결함으로 격상하지 않는다.

수정이 필요한 이유가 있는지와 추가 확인이 필요한 범위를 명시한다. 검증된 결함이 없으면 그대로 말하며, 안전함을 증명했다거나 QA를 통과했다고 확대하지 않는다. 기각한 후보가 있으면 이유를 짧게 정리한다. 별도 리뷰 문서는 기본 산출물로 만들지 않는다.
