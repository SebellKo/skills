# QA 실행 지침

QA 에이전트를 스폰할 때 이 지침과 작업별 맥락을 함께 전달한다.

## 필요한 원칙을 읽는다

메인과 QA 담당자는 아래 조건에 맞는 원칙 파일을 직접 읽고 검증·판정에 적용한다. 이미 현재 맥락에서 읽은 파일은 다시 읽지 않는다. 링크가 없으면 설치 목록에서 같은 이름을 찾고, 그래도 없으면 누락을 알린다. 원칙을 이유로 QA 범위를 임의로 넓히거나 제품 코드를 수정하지 않는다.

| 적용 상황 | 읽을 원칙 |
| --- | --- |
| 실제 동작을 확인하고 통과·실패를 판정할 때 | [prove-it-works](../../principles/principle-prove-it-works/SKILL.md) |
| 시나리오의 기대 결과나 자동화 검사를 정할 때 | [test-behavior-not-implementation](../../principles/principle-test-behavior-not-implementation/SKILL.md) |
| 사용 흐름·피드백·오류 경험을 확인할 때 | [experience-first](../../principles/principle-experience-first/SKILL.md) |
| 같은 전제의 수정·재시도가 같은 검사에서 두 번 이상 실패할 때 | [attack-the-premise](../../principles/principle-attack-the-premise/SKILL.md) |
| 긴 조사·실행 로그를 다룰 때 | [guard-the-context-window](../../principles/principle-guard-the-context-window/SKILL.md) |
| TypeScript 코드를 읽거나 검증 스크립트를 작성할 때 | [typescript-best-practices](../../typescript-best-practices/SKILL.md) |

## 실행 준비

저장소와 제공된 자료에서 다음을 확인한다. 이미 확인된 내용을 사용자에게 다시 묻지 않는다.

- **대상:** 사용자가 접근하는 화면·명령·API와 이번에 확인할 흐름.
- **실행:** 저장소의 실행 명령, 필요한 환경·인증·테스트 데이터, 사용할 주소.
- **조작:** 실제 사용자 경로를 실행할 도구와 기존 테스트 수단. 웹 직접 확인은 ego lite를 사용한다.
- **관찰:** 화면·응답·파일·저장 상태 등 기대 결과를 판단할 지점.
- **격리:** 다른 작업과 포트·세션·계정·데이터가 겹치는지, 자신이 만들고 정리할 자원.

프로세스나 HTTP 응답만 보고 준비 완료로 판단하지 않는다. 필요한 데이터와 인증을 갖춰 해당 흐름을 실제로 사용할 수 있어야 한다. 실행 중인 앱이 검증할 변경을 반영했는지 확인한다. 상태가 이상하면 먼저 주소·빌드·인증·준비 상태를 읽기 전용으로 점검한다.

## 로컬 서버 실행

- QA용으로 시작하는 로컬 서버는 **8080~8100 포트**를 사용한다. 범위 안에 대상 코드·환경과 일치하는 서버가 실행 중이면 재사용하고, 새로 실행할 때는 8080부터 빈 포트를 찾는다. 여러 서버가 필요하면 서로 다른 포트를 배정한다.
- 저장소가 지원하는 실행 옵션이나 환경변수로 포트를 지정한다. 포트를 맞추려고 제품 코드를 바꾸거나, 사용 중인 포트를 비우기 위해 다른 작업자의 프로세스를 종료하지 않는다.
- 실행 후 실제 수신 포트와 접속 URL을 확인한다. 개발 서버가 충돌을 피해 자동으로 다른 포트를 선택해도 이 범위를 벗어나면 QA를 진행하지 않는다. 범위 안의 포트로 다시 실행하고, 사용할 포트가 없거나 포트 지정이 불가능하면 원인과 필요한 조치를 보고한다.
- 브라우저에서는 `http://localhost:<선택한 포트>`를 기본 주소로 사용한다. 로그인 전에는 아래 계정 사용 기준도 확인한다.

## 로컬 테스트 계정

인증이 필요하면 `~/.codex/private/qa-accounts.json`을 참조한다. 이 파일은 스킬과 별도로 로컬에만 보관하며, GitHub·스킬 배포본·ZIP에 포함하지 않는다.

- 메인은 QA 에이전트에 파일 경로와 필요한 권한만 전달한다. 실행 담당자는 필요한 계정을 파일에서 읽고, 계정값을 프롬프트·명령 문자열에 복사하거나 파일 전체를 출력하지 않는다. ego lite에서는 가이드에 따라 런타임에서 파일을 읽어 로그인 입력에 사용한다.
- 현재 로그인 페이지의 origin(프로토콜·호스트·포트)이 파일의 `allowed_origins`와 정확히 일치하고, 현재 QA 대상 앱의 로그인 화면임을 확인한 뒤 계정을 사용한다. 이 조건을 충족하면 계정 파일 읽기와 로그인에 대해 사용자에게 다시 승인을 묻지 않는다.
- 리다이렉트로 로그인 주소가 바뀌면 입력 전에 origin을 다시 확인한다. `127.0.0.1`, HTTPS와 외부 주소를 등록된 HTTP localhost 주소와 같다고 취급하지 않는다. 허용 대상이 비어 있거나 다르면 사용할 서비스·환경을 확인한다. 파일이 없으면 계정이 필요한 검증만 미확인으로 남기거나 사용자에게 로컬 설정을 요청한다.
- 변경과 관련된 권한의 허용·차단 동작을 확인한다. 계정 이름만으로 실제 권한을 확정하지 않고 로그인 후 앱에서 확인하며, 계정을 바꿀 때 이전 세션이 남지 않았는지 점검한다.
- 보고에는 권한 이름을 사용한다. 이메일·비밀번호·인증 토큰은 로그·스크린샷·결과 문서·커밋에 남기지 않는다.

## 동작 확인

PR용 화면·사용자 흐름 근거를 배정받았다면 [PR 증거 수집 기준](pr-evidence.md)을 직접 읽고 적용한다. 관찰 결과와 실제 캡처를 반환하며 업로드·PR 게시를 대신 수행하지 않는다.

핵심 성공 흐름과 변경 위험에 맞는 실패·경계 조건을 선택한다. 유지해야 하는 동작과 공유 상태를 사용하는 주변 흐름도 포함한다. 선택표의 검증·동작 테스트 원칙에 따라 실행하고, UI는 해당 범위의 피드백과 오류 경험도 확인한다.

변경 전 확인에서는 직접 관찰한 행동과 결과를 남기고 코드에서만 추론한 내용은 구분한다. 이미 발생하는 문제와 확인할 수 없었던 조건도 메인에 전달한다.

예를 들어 저장 기능은 저장 행동 후 다시 열어 값이 유지되는지 확인한다. 같은 사실을 여러 수단으로 중복 확인하지 않는다.

모의 외부 서비스를 사용했다면 실제로 검증된 경계를 밝힌다. 반복할 가치가 있으면 기존 자동화 검사를 재사용하고, 간단한 일회성 확인마다 새 검증 체계를 만들지는 않는다.

## 실패 판단과 보고

실패하면 현재 상태를 다시 관찰하고 제품·환경·도구·기대 조건 중 어디에서 차이가 났는지 구분한다. 반복 실패는 선택표의 전제 검증 원칙에 따른다. 관찰한 사실과 원인 추정을 구분해 전달하고, 기대 조건을 약하게 바꿔 통과시키지 않는다.

메인에 다음을 반환한다. 모든 실행 로그를 나열할 필요는 없다.

- 실행 대상·버전 또는 확인 가능한 변경 상태와 환경.
- 시나리오별 사전 조건, 주요 행동, 기대 결과, 실제 결과, 통과·실패·미확인 판정과 근거.
- 실패의 최소 재현 절차, 기존 문제인지 새 회귀인지 판단할 근거 또는 불확실성.
- 검증하지 못한 범위와 이유, 남아 있는 테스트 자원.

메인이 판정을 검토할 수 있도록 실제 관찰 결과와 필요한 출력·스크린샷을 남기되, 별도 QA 문서는 만들 필요가 없다.

## 작업 경계와 정리

제품 코드를 수정하지 않는다. 다른 작업자가 같은 저장소를 사용할 수 있으므로 변경을 되돌리거나 검증을 위해 작업 트리를 과거 버전으로 전환하지 않는다. 테스트 준비에 필요한 임시 자원은 지정된 범위에만 만든다.

테스트 계정·데이터를 우선 사용한다. 결제·외부 발송·사용자 데이터 삭제 등 실제 효과를 만드는 조작은 이미 승인된 범위를 확인한다. 테스트 모드라는 이름만으로 외부 효과가 없다고 가정하지 않는다.

자신이 만든 프로세스·테스트 데이터만 정리하고 사용자 세션과 자원을 보존한다. 프로세스 이름으로 일괄 종료하거나 브라우저 프로필 전체를 초기화하지 않는다. ego lite의 공간 종료·제어권 반환은 현재 가이드를 따르고, 결과 검토에 필요한 증거는 정리하면서 지우지 않는다.
