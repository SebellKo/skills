# 기능 QA

메인이 검증 범위와 기준을 정리하고, 구현을 담당하지 않은 QA 서브에이전트가 실제 동작을 확인한다. 메인은 관찰 근거를 검토해 결과를 판단한다. 사용자 설명, 코드, 변경 내역, 실행 중인 앱만으로도 시작할 수 있다.

## 1. 확인할 동작과 시점을 정한다

메인은 [QA 실행 지침](references/qa-brief.md)의 원칙 선택표를 읽고, 작업에 해당하는 원칙 파일을 직접 읽는다. `dev-mode`나 앞 단계 스킬의 실행 여부와 관계없이 적용한다.

요청과 현재 변경 상태에 맞춰 필요한 작업을 선택한다.

- **변경 전 기준 확인:** 현재 사용자 흐름과 결과를 관찰하고, 바뀌어야 할 동작·유지할 동작·영향받을 주변 동작을 구분한다.
- **변경 후 검증:** 요구한 동작이 구현됐는지, 유지할 동작과 주변 흐름이 정상인지 확인한다. 수정 후에는 실패했던 흐름과 수정으로 영향받는 범위를 다시 확인한다.

관련 코드의 호출 관계, 공유 상태·저장소·캐시, 진입 경로를 살펴 검증 범위를 정한다. 변경 파일에만 한정하거나 근거 없이 앱 전체로 넓히지 않는다. 기존 요구사항 번호나 완료 조건이 있으면 그대로 연결한다.

현재 동작과 기대 동작을 구분한다. 기존 버그를 유지 조건으로 삼지 않으며, 기대 결과가 불명확해 판정이 달라지는 경우에만 사용자에게 확인한다. 변경 전 관찰이 없더라도 현재 기능은 검증할 수 있다. 다만 코드에서 추론한 과거 동작을 직접 관찰한 기준으로 보고하지 않는다.

## 2. QA 에이전트에 위임한다

기본은 QA 에이전트 한 명이다. `model: "gpt-6.2-sol"`, `reasoning_effort: "medium"`, `fork_turns: "none"`으로 스폰한다. 이 모델이나 위임 기능을 사용할 수 없다면 제약을 알리고 대안을 확인하며, 조용히 다른 모델로 대체하지 않는다.

QA 실행 지침과 선택한 원칙의 실제 파일 경로를 전달하고 직접 읽도록 명시한다. 요약이나 스킬 이름 나열로 읽기를 대신하지 않는다. QA 담당자는 작업 중 새로 해당하는 원칙도 읽고, 반환할 때 실제 읽은 원칙과 판단에 영향을 준 내용을 짧게 남긴다. 다음 정보를 함께 전달한다.

- 목적과 시점, 변경 범위, 사용자 관점의 기대 결과와 근거.
- 저장소·변경 내역·실행 URL, 확인된 실행 방법과 필요한 테스트 데이터.
- 변경 전 관찰 요약이 있으면 대상 버전·환경, 사용자 행동과 결과, 유지 조건, 기존 문제, 미확인 항목.
- QA가 사용할 인스턴스·브라우저 공간과 수정 가능한 테스트 자원의 범위.
- 구현 코드 수정 없이 검증하고, 제품 문제·환경 또는 검증 도구 문제·기대 조건의 불일치를 구분해 보고할 책임.

변경 전·후를 이어서 검증할 때는 가능하면 같은 QA 에이전트를 재사용한다. 메인은 기준 요약과 증거 위치를 유지해 새 에이전트에도 전달할 수 있게 한다.

여러 에이전트가 필요하면 독립적인 흐름으로 나누고, 브라우저·계정·데이터까지 충돌하지 않는지 확인한다. 같은 인스턴스나 세션을 여러 에이전트가 동시에 조작하지 않는다. QA 에이전트는 추가 에이전트를 스폰하지 않는다.

## 3. 실제 사용자 경로로 확인한다

웹 화면의 직접 확인은 **ego lite**로 수행한다. 실행 담당자는 설치된 `ego-browser` 스킬을 읽고 `ego-browser skill`이 반환하는 현재 가이드를 따른다. 사용할 수 없으면 해당 UI 검증을 미확인으로 남기고 원인을 보고한다. 다른 브라우저로 임의 전환하지 않는다.

CLI·API 등은 해당 사용자가 실제 사용하는 인터페이스로 확인한다. 기존 자동화 테스트와 실행 도구를 활용하며, 준비·관찰·정리 방법은 QA 실행 지침을 따른다.

## 4. 근거를 검토하고 결과를 전달한다

메인은 QA가 반환한 사용자 행동, 실제 결과, 실행 대상과 증거를 기대 조건과 대조한다. 중요한 실패나 근거가 부족한 판정은 직접 확인하거나 QA에 재현을 요청한다. 충분한 근거가 있는 모든 흐름을 다시 실행할 필요는 없다.

각 항목을 **통과·실패·미확인**으로 구분한다. 실행하지 못한 항목이나 일부만 확인한 흐름을 통과에 포함하지 않는다. 변경 전 근거가 부족하면 현재 실패는 보고하되, 이번 변경으로 생긴 회귀라고 단정하지 않는다.

결과는 작업 규모에 맞춰 대화에 간결하게 남긴다.

- 변경 전 확인이면: 관찰한 흐름과 결과, 바뀔 조건·유지 조건, 주변 영향, 미확인 항목.
- 변경 후 검증이면: 확인한 범위와 판정, 실패의 재현 절차·기대값·실제값, 중요한 증거, 미확인 범위와 이유.

QA 문서나 기능 목록 파일을 기본 산출물로 만들지 않는다. 필요한 스크린샷·실행 출력은 검토 가능한 증거로 제시한다. QA만 요청받았다면 제품 코드를 고치거나 다음 작업을 자동으로 시작하지 않는다.
