# PR 생성

현재 변경이 해결한 문제와 검토 가능한 결과를 보여 준다. PR 생성 요청 또는 `dev-mode`의 위임에는 해당 작업 브랜치의 커밋·push와 PR 게시가 포함된다. 이미 승인된 범위는 다시 확인받지 않는다. 병합·배포는 별도 요청 범위다.

## 1. 변경과 게시 대상을 확인한다

실제 diff, 기준·작업 브랜치, 대상 저장소, 관련 Issue, 구현·리뷰·QA 결과를 읽는다. 사용자와 다른 작업자의 변경을 구분하고 이번 작업만 커밋한다. 기존 작업 브랜치와 PR을 재사용하고, 없다면 기준 브랜치를 확인해 작업 브랜치를 준비한다. 커밋·push는 필요할 때만 수행하며 무관한 변경을 포함하거나 강제로 이력을 덮어쓰지 않는다.

같은 저장소·head·base에 이미 PR이 있으면 갱신한다. 저장소의 Pull Request 템플릿과 작성 규칙을 읽고 그 구조를 유지한다. 템플릿이 여러 개면 작업에 맞는 것을 고른다. Assignee는 인증된 GitHub 사용자 본인으로 지정하며, 기존의 다른 Assignee를 임의로 제거하지 않는다.

## 2. 본문과 근거를 준비한다

- **목적과 변경:** 해결한 문제와 사용자가 경험하는 결과를 먼저 설명하고, 리뷰에 필요한 구현·이전·호환성 정보만 덧붙인다.
- **Issue:** 관련 Issue를 링크한다. 작업 전체를 해결하고 기본 브랜치로 병합하는 PR에는 `Closes #번호`를 사용한다. 일부 범위만 해결하거나 다른 브랜치가 대상이면 일반 참조로 연결하고 자동 종료를 약속하지 않는다. 독립 PR 요청에 Issue가 없으면 이를 이유로 새 Issue를 자동 생성하지 않는다.
- **화면 비교:** 시각적 확인이 필요한 변경에는 실제 업로드한 스크린샷을 `변경 전 (Before) | 변경 후 (After)` 표로 배치한다. 필요한 상태별로 비교하고, 비교 조건과 차이가 있으면 짧게 설명한다.
- **사용자 확인 방법:** 실제 사용자 동작의 확인이 필요하면 사전 조건·권한·테스트 데이터, 시작 URL 또는 메뉴, 번호 순서의 행동과 각 단계의 기대 결과를 적는다. 시작 위치가 찾기 어렵거나 요청받았다면 진입 영역을 표시한 실제 화면을 함께 넣는다.
- **검증 결과:** 직접 실행한 검사와 관찰, 미실행·실패·미확인을 구분한다. 리뷰어가 따라 할 절차를 작성했다는 사실과 에이전트가 직접 검증했다는 사실은 구분한다.

화면·사용자 흐름 자료가 필요하면 [QA 증거 수집 기준](../qa-feature/references/pr-evidence.md)을 읽는다. 기존 증거가 최종 코드와 일치하는지 확인한다. 자료가 부족하면 `qa-feature`에 필요한 캡처·흐름 확인만 요청하고 실제 파일과 관찰 결과를 전달받는다. 이전 화면은 실제 이전 버전을 확인할 수 있을 때만 보충하며, 확보하지 못하면 이유를 적는다. 화면 변화가 없거나 사용자 플로우가 해당하지 않으면 해당 섹션을 생략한다.

## 3. 게시하고 실제 PR을 확인한다

[prove-it-works](../principles/principle-prove-it-works/SKILL.md)와 [게시·첨부 지침](references/publishing.md)을 읽고 게시한다. 필수 검사나 필요한 화면 근거가 남았으면 누락과 이유를 표시하고 Draft로 게시하거나 기존 Draft를 유지한다. 이미 열린 일반 PR을 Draft로 바꿔야 한다면 이유를 명시한다. 검증되지 않은 상태를 완료로 보고하지 않는다.

게시 후 PR의 저장소·head·base, 제목·본문, Issue 참조, Assignee, Draft 상태와 첨부 이미지를 확인한다. 본문에 로컬 경로·임시 URL·작성용 표시가 남지 않게 한다. 이미지가 있으면 ego lite에서 실제 PR의 표·이미지·진입 표시가 읽히는지도 확인한다. 접근·게시가 막히면 본문과 증거를 보존하고 실패 범위와 다음 조건을 반환한다.

최종 결과에는 PR·Issue 링크, 확인한 검증 범위와 남은 사항을 짧게 담는다. PR 게시만으로 QA·CI 통과나 병합을 주장하지 않는다.
