# 코드 설계

메인은 공통 근거와 평가 기준을 준비하고, 서브에이전트들이 만든 설계를 읽어 하나의 설계안으로 정리한다. 사용자 설명만으로도 시작할 수 있으며, 기존 요구사항이나 설계안이 있으면 이어받는다.

ISO 24495-1:2023의 쉬운 언어 원칙에 따라 선택한 구조와 이유를 먼저 설명하고, 프로젝트에서 쓰는 용어를 사용한다.

## 1. 메인이 문제와 평가 기준을 정한다

- 해결할 동작, 완료 조건, 유지할 계약과 제약을 추린다. 구조를 결정하는 데 꼭 필요한 제품 선택만 묻는다. 이미 합의했거나 위임한 항목은 다시 확인받지 않는다.
- 기존 코드의 관련 진입점, 호출부, 상태 소유자, 외부 의존성, 테스트와 유사 기능을 조사한다. 책임이나 계층을 바꿀 때는 관련 PR·기록에서 기존 선택의 이유도 확인한다.
- 제공된 백엔드 PR은 바로 참조할 수 있는 계약으로 사용한다. 요청·응답, 권한, 상태와 오류를 확인하고 병합·배포 여부를 미결정 사항으로 만들지 않는다.
- 모든 후보에게 줄 공통 설명에 목표, 제약, 코드·자료 위치, 확인한 사실과 미확인 가정을 담는다. 새 작업은 주변 코드가 없다는 점을 명시한다. 메인이 선호하는 해결안이나 다른 후보의 결과는 넣지 않는다.
- 후보를 보기 전에 평가 기준을 정한다. 요구사항과 계약 준수를 필수 조건으로 두고, 호출자가 알아야 할 복잡성, 상태 소유권, 변경 범위, 검증 가능성 중 이번 작업에 중요한 기준을 선택한다. 성능은 실제 요구나 근거가 있을 때 포함한다.

## 2. 서브에이전트들이 독립적으로 설계한다

기본 3개, 범위가 작은 작업은 2개의 후보를 만든다. 사용자가 수를 지정하면 따른다. 각 후보는 동일한 문제 전체를 설계하며, 작업을 파일별로 분담하지 않는다.

Codex의 `collaboration.spawn_agent`에 다음 값을 명시한다.

- `agent_type: "default"`
- `model: "gpt-6.2-sol"`
- `reasoning_effort: "high"`
- `fork_turns: "none"`

각 에이전트에게 공통 설명과 [후보 설계 지침](references/candidate-brief.md)의 내용을 전달한다. 대화 이력을 상속하지 않으므로 사용자 결정, 필요한 자료와 작업 경로를 공통 설명에 포함한다. 같은 자료를 직접 읽게 하고, 후보 간 결과 공유는 완료 후까지 미룬다.

동시 실행 한도 안에서 병렬로 시작한다. 후보는 저장소를 수정하지 않고 설계와 근거를 반환한다. 실험이 필요하면 후보별 임시 디렉터리를 배정하고, 공유 코드와 다른 후보의 파일을 변경하지 않도록 한다.

지정 모델을 실행할 수 없으면 그 사실을 알리고 다른 모델로 임의 대체하지 않는다. 실패한 후보와 확보한 후보 수를 공개한다. 완료된 후보가 2개 미만이면 독립 비교가 끝났다고 보고하지 않는다.

## 3. 메인이 비교하고 기준 설계를 고른다

모든 후보의 설계와 근거를 읽는다. 요구사항·계약 위반이나 근거 없는 전제를 먼저 확인하고, 후보 번호별로 사전에 정한 기준에 따라 비교한다. 문서 길이나 표현의 그럴듯함, 다수 의견 자체를 선택 근거로 삼지 않는다.

다음 문제가 있는지 실제 호출 예제와 상태 흐름에서 확인한다.

- 호출자가 내부 처리 순서나 여러 곳의 같은 정책을 알아야 한다.
- 같은 상태를 여러 곳에서 따로 갱신하거나 같은 목록·규칙을 수동으로 맞춘다.
- 내부 처리 방식을 공개 옵션으로 노출하거나 책임 없이 전달만 하는 계층을 추가한다.
- 한 요구사항을 바꾸려면 관련 없는 여러 사용처를 동시에 고쳐야 한다.

유효한 대안이 있는 중요한 선택에서는 책임 배치나 인터페이스가 다른 구조를 비교한다. 후보가 같은 구조로 모였으면 제약 때문에 그런지 확인하고, 차이를 만들기 위한 대안은 추가하지 않는다. 후보가 서로 다른 요구사항을 전제로 했다면 공통 설명을 바로잡아 영향을 받는 후보를 다시 설계하게 한다.

필수 조건을 만족한 후보 중 기준 설계 하나를 선택하고 이유와 받아들이는 단점을 적는다. 만족하는 후보가 없으면 위반 사항을 바탕으로 재설계한다. 같은 막힘이 반복되면 누락된 근거나 결정을 남기고 최종안으로 확정하지 않는다.

## 4. 좋은 부분을 통합하고 확인한다

다른 후보에서 가져올 부분은 기준 설계의 책임, 타입, 상태 소유권과 오류 규칙에 맞을 때 반영한다. 가져온 부분과 출처 후보, 채택 이유를 기록한다. 더 나아지는 부분이 없으면 기준 설계를 그대로 사용한다.

최종안의 호출 예제와 타입·반환값·오류 규칙을 맞추고, 대표적인 성공과 실패 흐름을 따라간다. 변경되는 호출부, 공개 export, 설정, 저장·전송 형식과 관련 테스트를 확인한다. 계약을 바꾸면 영향을 받는 사용처와 호환·이전 방법을 포함한다.

설계 선택을 좌우하는 라이브러리 동작이나 동시성 가정은 최소 실험이나 기존 테스트로 확인한다. 실행 결과와 미검증 가정을 구분한다. 반복적인 예외 처리나 형변환이 필요하면 규칙을 덧붙이기 전에 해당 책임과 인터페이스를 다시 검토한다.

## 5. 하나의 설계안으로 제공한다

작업 크기에 맞춰 아래 내용을 담는다. 작은 변경은 짧은 설명과 코드 예제로 충분하다. 기존 설계 문서가 있으면 해당 부분을 갱신한다.

- **문제와 제약:** 설계할 동작, 유지할 계약, 주요 근거. 요구사항 번호가 있으면 연결한다.
- **추천 구조:** 호출 예제, 타입·시그니처, 책임 배치와 상태·데이터 흐름. 기존 파일 위치와 새로 제안한 위치를 구분한다.
- **비교와 통합:** 실제 후보 수와 사용 모델, 기준별 비교, 선택한 후보와 이유, 다른 후보에서 반영하거나 제외한 주요 부분. 후보 실패가 있으면 표시한다.
- **변경 영향과 검증:** 바뀌는 사용처, 필요한 이전 방법, 확인할 시나리오와 수행한 실험 결과.
- **남은 결정:** 미확인 가정이나 제품 결정, 설계에 미치는 영향.

해당하지 않는 항목은 생략한다. 모듈 관계나 상태 변화가 글보다 잘 드러날 때만 도식을 덧붙인다.
