# 코드 설계

사용자 설명이나 기존 요구사항·설계안을 입력으로 받아, 호출 예제와 인터페이스 중심의 설계안을 만든다. 요구사항 문서나 특정 스킬의 사전 실행을 전제로 하지 않는다. 이미 결정된 제약은 이어받고 이번 설계에 필요한 부분을 보완한다.

ISO 24495-1:2023의 쉬운 언어 원칙에 따라 선택한 구조와 이유를 먼저 설명하고, 프로젝트에서 쓰는 용어를 사용한다.

## 1. 설계의 근거를 확인한다

- 해결할 동작, 완료 조건, 유지해야 할 계약과 제약을 추린다. 구조를 바꾸는 데 꼭 필요한 제품 결정만 묻고, 기술 선택은 근거와 함께 제안한다. 이미 합의했거나 위임한 항목은 다시 확인받지 않는다.
- 기존 코드가 있으면 관련 진입점에서 호출부, 상태 소유자, 외부 의존성, 테스트까지 따라간다. 유사한 기능과 프로젝트 관례를 확인해 재사용할 부분을 찾는다. 책임이나 계층을 바꿀 때는 관련 PR·기록에서 기존 선택의 이유를 확인한다.
- 제공된 백엔드 PR은 바로 참조할 수 있는 계약으로 사용한다. 요청·응답, 권한, 상태와 오류를 확인하고 병합·배포 여부를 설계의 미결정 사항으로 만들지 않는다.
- 근거에는 파일·심볼·커밋이나 자료 링크를 붙인다. 코드가 없는 새 작업은 제공된 제약을 기준으로 설계하고, 확인한 사실과 가정을 구분한다. 자료 접근 실패를 기능 미지원으로 해석하지 않는다.

## 2. 호출하는 쪽부터 구조를 그린다

먼저 실제 사용 예제를 쓴다. 호출자가 무엇을 전달하고, 어떤 결과나 오류를 받고, 어떤 순서·수명 규칙을 알아야 하는지 드러낸다. 예제에서 필요한 타입, 함수 시그니처와 책임 배치를 도출한다. 작은 변경은 한 가지 예제로 충분하다.

- **책임:** 함께 바뀌는 규칙과 지식은 같은 곳에서 관리한다. 호출자가 내부 처리 순서를 조율하거나 여러 곳에 같은 정책을 구현하게 만들지 않는다.
- **인터페이스:** 호출자가 알아야 할 조건과 옵션을 줄이고 복잡한 처리는 내부에 모은다. 기존 계약과 타입을 재사용한다. 새 계층이나 데이터 변환은 실제로 숨길 복잡성이나 격리할 변화가 있을 때 도입한다.
- **상태와 흐름:** 각 상태의 소유자와 갱신 경로를 정한다. 원본 상태와 파생 값을 구분하고, 같은 정보를 여러 곳에서 따로 갱신하게 만들지 않는다. 관련된 상태 전이, 실패·취소·재시도와 동시 요청의 결과를 설명한다.
- **외부 의존성:** 검증과 부수 효과가 어디서 일어나는지 정한다. 교체나 테스트에 필요한 접점은 가능한 한 내부에 두고, 기존 테스트 수단으로 충분한 곳에 별도 인터페이스나 어댑터를 만들지 않는다.

호출 예제와 타입·오류·상태 규칙이 서로 맞는지 확인한다. 한 번의 사용자 동작이 어느 책임을 거쳐 어떤 결과를 만드는지 따라갈 수 있어야 한다.

## 3. 선택이 필요한 부분을 비교한다

책임 배치나 공개 계약처럼 바꾸기 어려운 선택에 유효한 대안이 있으면 구조가 다른 안을 비교한다. 기존 구조를 유지하는 안도 후보로 삼는다. 명확한 소규모 변경에는 형식적인 대안을 만들지 않는다.

비교 기준은 호출자가 알아야 할 복잡성, 변경이 퍼지는 범위, 상태 소유권, 검증 가능성과 실제 요구된 성능이다. 추천안과 받아들이는 단점을 짧게 남긴다. 같은 규칙을 여러 곳에 고치게 하는 구조, 내부 정보를 노출하는 옵션, 책임 없이 전달만 하는 계층은 줄인다.

라이브러리 동작이나 동시성처럼 설계 선택을 좌우하는 사실이 불확실하면, 임시 공간에서 최소 실험이나 기존 테스트를 실행해 확인한다. 실행 결과와 아직 검증하지 못한 가정을 구분한다.

## 4. 변경 영향과 검증 방법을 확인한다

- 바뀌는 호출부, 공개 export, 설정, 저장·전송 형식과 관련 테스트를 확인한다. 기존 계약을 바꾸면 영향을 받는 사용처와 호환·이전 방법을 설계에 포함한다.
- 대표 호출과 중요한 실패 사례를 인터페이스를 통해 어떻게 확인할지 정한다. 외부 시스템은 기존 테스트 환경이나 필요한 대체 수단을 명시한다. 내부 함수의 호출 순서보다 관찰 가능한 결과를 기준으로 삼는다.
- 호출자마다 같은 예외 처리가 필요하거나 설계 밖의 옵션·형변환이 반복해서 필요하다면, 추가 규칙을 붙이기 전에 책임 배치와 인터페이스를 다시 살핀다.

## 5. 설계안을 제공한다

작업 크기에 맞춰 아래 내용을 담는다. 작은 변경은 짧은 설명과 코드 예제로 충분하다. 기존 설계 문서가 있으면 해당 부분을 갱신한다.

- **문제와 제약:** 설계할 동작, 유지할 계약, 주요 근거. 요구사항 번호가 있으면 연결한다.
- **추천 구조:** 호출 예제, 타입·시그니처, 책임 배치와 상태·데이터 흐름. 파일 위치는 기존 위치와 새로 제안한 위치를 구분한다.
- **선택 이유:** 실제 비교한 대안, 추천 이유와 받아들인 단점.
- **변경 영향과 검증:** 바뀌는 사용처, 필요한 이전 방법, 확인할 시나리오와 수행한 실험 결과.
- **남은 결정:** 미확인 가정이나 제품 결정, 설계에 미치는 영향.

해당하지 않는 항목은 생략한다. 모듈 관계나 상태 변화가 글보다 잘 드러날 때만 도식을 덧붙인다.
