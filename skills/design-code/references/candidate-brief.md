# 후보 설계 지침

공통 설명의 문제 전체를 독립적으로 설계한다. 제공된 코드와 근거를 직접 확인하고, 기존 계약과 관례를 조사한다. 여러 에이전트가 같은 파일 시스템을 사용하므로 공유 코드나 다른 후보의 파일을 수정하지 않는다. 추가 에이전트는 생성하지 않는다.

## 호출 예제에서 구조를 도출한다

실제 사용 예제를 먼저 쓴다. 호출자가 전달할 값, 받을 결과와 오류, 알아야 할 순서·수명 규칙을 보여 준다. 여기에서 필요한 타입, 함수 시그니처와 책임 배치를 도출한다.

- 함께 바뀌는 규칙과 지식은 같은 곳에서 관리하고, 작은 인터페이스 뒤에 복잡한 처리를 모은다.
- 기존 계약과 타입을 재사용한다. 새 계층·데이터 변환은 숨길 복잡성이나 격리할 변화가 있을 때 도입한다.
- 각 상태의 소유자와 갱신 경로를 정한다. 원본과 파생 값을 구분하고 관련된 실패·취소·재시도·동시 요청의 결과를 설명한다.
- 검증과 부수 효과가 일어나는 위치를 정한다. 교체나 테스트를 위한 접점은 필요한 만큼만 두고, 기존 테스트 수단을 우선한다.
- 바뀌는 사용처와 공개 계약, 필요한 이전 방법을 확인한다. 대표 성공·실패를 인터페이스에서 관찰 가능한 결과로 검증할 방법을 제시한다.

기존 구조를 유지하는 안도 검토한다. 중요한 선택에 유효한 대안이 있으면 구조가 다른 안과 비교하고, 추천 이유와 단점을 적는다. 차이를 만들기 위해 불필요한 계층이나 옵션을 추가하지 않는다.

## 반환할 내용

1. 확인한 근거와 가정.
2. 추천 구조와 호출 예제, 타입·시그니처.
3. 책임 배치, 상태·데이터 흐름과 오류 처리.
4. 실제 검토한 대안, 추천 이유와 단점.
5. 변경 영향, 검증 방법과 수행한 실험 결과.
6. 해결하지 못한 결정이나 위험.

설계 선택을 좌우하는 사실에 한해 배정된 임시 공간에서 최소 실험을 할 수 있다. 실행하지 않은 검증은 제안으로 표시한다. 사용자에게 물어야 할 결정은 결과에 남겨 메인이 취합할 수 있게 한다.
