# 코드 구현

메인은 작업 범위와 완료 조건을 정하고, 서브에이전트가 작성한 코드를 검토·검증한다. 사용자 설명만으로 시작할 수 있으며, 기존 요구사항과 설계가 있으면 그 결정을 이어받는다.

ISO 24495-1:2023의 쉬운 언어 원칙에 따라 구현 결과, 검증 근거와 남은 문제를 구체적으로 설명한다.

## 1. 메인이 구현 범위와 검증 기준을 정한다

- 원하는 동작, 유지할 동작과 계약, 이번 변경의 완료 조건을 정리한다. 기존 코드의 진입점, 호출부, 관련 테스트와 프로젝트 관례를 조사한다. 구현에 꼭 필요한 제품 결정만 묻고, 이미 합의했거나 위임한 항목은 다시 확인받지 않는다.
- 설계가 있으면 타입·인터페이스·상태 소유권을 작업 조건에 포함한다. 설계가 없으면 기존 구조에서 필요한 최소 변경을 정리한다. 특정 문서나 다른 스킬의 사전 실행을 요구하지 않는다.
- 시작 코드와 사용자·다른 작업자의 기존 변경을 확인해 이번 작업과 구분한다. Git 저장소라면 기준 커밋, 수정·추가 파일과 관련 diff를 기록한다. 기존 변경 위에서 작업해야 하면 그 내용도 전달한다.
- 검증 기준은 구현 전에 정한다. 완료 조건에 맞는 실행 시나리오와 기존 테스트·타입 검사·빌드 명령을 찾는다. 필요한 기존 검사를 실행해 원래 있던 실패와 새 실패를 구분한다.

## 2. 구현 담당자와 작업 공간을 정한다

기본은 서브에이전트 1개가 구현하고 메인이 검토하는 방식이다. 변경이 작아도 구현 담당자와 검토자를 분리한다. 서로 독립적인 범위가 실제로 있으면 담당 파일과 공유 계약을 정해 병렬로 위임한다. 같은 파일·상태를 함께 수정해야 하는 부분은 한 담당자에게 맡기거나 순서대로 진행한다.

Codex의 `collaboration.spawn_agent`에 다음 값을 명시한다.

- `agent_type: "worker"`
- `model: "gpt-6.1-sol"`
- `reasoning_effort: "high"`
- `fork_turns: "none"`

각 담당자에게 목표·완료 조건, 합의한 설계, 코드·자료 위치, 기준 상태, 담당 파일·책임, 작업 경로, 검증 명령과 [구현 담당자 지침](references/worker-brief.md)의 내용을 전달한다. 대화 이력을 상속하지 않으므로 필요한 사용자 결정과 제약을 설명에 포함한다. 같은 코드베이스에서 다른 작업도 진행될 수 있으며, 기존 변경을 되돌리지 말아야 한다고 명시한다.

한 담당자는 현재 작업 공간에서 일할 수 있다. 서로 겹치는 구현 후보를 비교할 때는 같은 시작 상태를 가진 별도 worktree나 복사본을 배정한다. 커밋만 복제해 필요한 미커밋 변경이 빠지지 않도록 확인한다. 동시 실행은 도구의 한도 안에서 진행한다.

지정 모델을 실행할 수 없으면 그 사실을 알린다. 다른 모델이나 메인의 직접 구현으로 조용히 대체하지 않는다.

## 3. 메인이 실제 변경을 검토한다

담당자의 요약뿐 아니라 기준 상태 대비 실제 diff와 연결된 호출부·테스트를 읽는다. 아래 항목을 확인한다.

- 요청한 동작과 합의한 계약을 충족하고 관련 호출부·설정·테스트가 함께 반영됐는가.
- 실패·경계 상황에서 기존 검증과 오류 처리를 유지하는가.
- 기존 패턴을 재사용하며 불필요한 계층, 옵션, 의존성이나 무관한 변경을 추가하지 않았는가.
- 사용자와 다른 작업자의 변경을 보존했는가.
- 테스트가 구현을 그대로 따라 쓰거나, 잘못된 동작에 맞춰 기대값을 약하게 바꾸지 않았는가.

문제를 찾으면 해당 파일, 재현 조건, 기대 결과를 구현 담당자에게 전달해 수정하게 한다. 수정된 diff와 관련 동작을 다시 확인한다. 설계를 바꿔야 하는 근거가 나오면 그 영향부터 정리하고, 기존 계약을 임의로 변경해 통과시키지 않는다.

같은 실패가 반복되면 원인과 전제를 다시 조사한다. 추가 진행에 필요한 결정이나 실행 환경이 없으면 막힌 범위와 필요한 조건을 보고하며, 미완성 작업을 완료로 표시하지 않는다.

## 4. 적용된 결과를 검증한다

메인이 최종 작업 공간에서 핵심 완료 조건과 영향받는 기존 검사를 직접 실행한다. 담당자의 통과 보고만으로 완료를 판단하지 않는다. 실행할 수 없는 검사는 이유와 미검증 범위를 남긴다. 구현이나 통합으로 검증 대상이 바뀌면 해당 결과에서 다시 검사한다.

분담한 작업은 공유 계약과 연결 흐름까지 확인한다. 각 담당자의 테스트가 통과해도 통합 결과가 통과했다고 가정하지 않는다.

여러 구현 후보를 비교하기로 했다면 같은 완료 조건과 검증 방법을 적용한다. 계약 위반·회귀가 있는 후보를 제외하고, 복잡성·변경 범위·기존 코드와의 일관성으로 기준 구현 하나를 고른다. 다른 후보의 부분은 그 구현과 호환되고 이점이 분명할 때만 반영하고, 통합 결과를 다시 검증한다. 비교를 위해 합의한 설계를 후보마다 다르게 바꾸지 않는다.

## 5. 구현 결과를 제공한다

변경된 동작과 주요 파일, 실제 수행한 검증과 결과, 해결하지 못한 문제를 정리한다. 요구사항 번호가 있으면 구현·검증 근거를 연결한다. 위임한 범위와 사용 모델, 분담이나 후보 통합이 있었다면 그 결과를 짧게 남긴다.
