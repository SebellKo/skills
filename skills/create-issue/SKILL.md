# 작업 Issue

무엇을 왜 진행하며 어디까지 완료할지를 기록한다. 사용자 설명만으로 시작할 수 있고, 기존 요구사항·Issue가 있으면 이어받는다. 명시적인 Issue 작업 요청 또는 `dev-mode`의 위임 범위 안에서 게시한다.

## 대상과 기존 작업을 확인한다

- 사용자 지정 저장소와 Issue를 우선한다. 지정이 없으면 작업 저장소의 remote와 관련 Issue를 확인한다. 같은 목적의 열린 Issue가 있으면 이어받고, 제목만 비슷한 다른 작업을 덮어쓰지 않는다.
- 저장소의 Issue 템플릿·폼과 작성 규칙을 읽는다. 필수 항목과 적절한 분류를 적용하되, 확인하지 않은 담당자·라벨·기한을 만들지 않는다. 대상 저장소가 모호할 때만 확인한다.
- 목표와 대략적인 범위가 정해지면 등록할 수 있다. 미결정을 확정 요구사항처럼 쓰지 않고, 이후 합의된 요구사항 변경을 같은 Issue에 반영한다.

## 작업 중심으로 작성한다

저장소 형식에 다음 내용을 작업 크기에 맞춰 담는다. 짧은 작업에 빈 섹션을 채우지 않는다.

- 배경과 해결할 문제, 작업 목표.
- 요구사항과 포함·제외 범위. 기존 요구사항 번호가 있으면 유지한다.
- 제약과 유지할 동작, 필요한 외부 의존성.
- 관찰 가능한 완료 조건.
- 관련 디자인, 백엔드 PR, 기존 논의와 미결정 사항.

파일별 수정 목록, 상세 아키텍처나 구현 순서를 기본 본문에 넣지 않는다. 이미 합의된 기술 제약은 요구사항으로 구분하고, 설계가 필요하면 관련 자료를 링크한다. 기존 Issue를 갱신할 때 다른 작성자의 논의와 유효한 요구사항을 보존한다.

## 게시하고 확인한다

게시 전 [prove-it-works](../principles/principle-prove-it-works/SKILL.md)를 읽는다. 연결된 GitHub 도구를 우선하고, 필요한 기능이 없으면 `gh`나 GitHub UI를 사용한다. 여러 줄 본문은 구조화된 도구 인자 또는 임시 UTF-8 파일과 `--body-file`로 전달한다. 사용자 문구를 셸 코드로 보간하지 않는다.

이미 승인된 생성·갱신을 다시 확인받지 않는다. 응답이 실패하거나 불명확하면 먼저 실제 Issue 존재 여부를 조회하고 재시도해 중복을 피한다. 게시 후 제목·본문·저장소와 URL을 다시 읽어 의도대로 반영됐는지 확인한다.

권한·인증·저장소 설정 때문에 게시할 수 없으면 작성한 본문과 원인을 반환한다. 생성하지 않은 Issue 번호나 URL을 만들지 않는다. Issue 생성만 요청받았다면 구현·PR 생성·Issue 종료까지 자동으로 진행하지 않는다.
